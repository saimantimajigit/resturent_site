# Phase 12.3 hardening review

## Scope and result

This change adds focused security, accessibility, performance, and reliability protections. It does not change the database schema or run migrations. PostgreSQL reported all six existing migrations applied. A read-only Prisma schema diff found broad pre-existing schema-to-database drift; no reconciliation was attempted.

## Findings and disposition

| Severity | Evidence and impact | Change and validation | Remaining risk |
| --- | --- | --- | --- |
| High | Production rate limits previously derived the client identity from request forwarding headers, which a direct caller can spoof unless ingress overwrites them. | Production now accepts only the configured header names `x-real-ip`, `cf-connecting-ip`, or `true-client-ip`; the selected value must parse as one IPv4 or IPv6 address. Commas, malformed values, unsupported header names, and missing configuration are rejected as an address identity. Local tests confirm caller changes to `x-forwarded-for` do not change a configured `x-real-ip` identity. | **Deployment prerequisite:** configure `SAVORE_TRUSTED_CLIENT_IP_HEADER` and a trusted reverse proxy that removes any incoming client-supplied copy of that header, writes the actual client IP itself, and prevents direct access that bypasses the proxy. If the setting is absent, rate limiting uses the fixed `trusted-proxy-unconfigured` bucket. If the setting exists but the header is missing/malformed, it uses the fixed `unknown` bucket. This prevents spoof-based quota evasion but lets a caller sharing that fallback consume the common IP quota. Unit tests simulate the helper only; deployed ingress behavior and direct-origin network restrictions require deployment verification. |
| Medium | Production lacked frame, content-type, referrer, and browser capability protections; Next.js exposed its framework version header. | Added `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: strict-origin-when-cross-origin`, and `Permissions-Policy: camera=(), microphone=(), geolocation=()`; disabled `X-Powered-By`. Current CSP is exactly `base-uri 'self'; object-src 'none'; frame-ancestors 'none'`. Production HTTP checks verified these headers. **The application does not emit HSTS.** | **This is partial CSP hardening, not a complete CSP.** It does not restrict `default-src`, `script-src`, `style-src`, `img-src`, `font-src`, `connect-src`, or `form-action`; script, style, image, font, and connection sources therefore remain unrestricted by CSP. The current app loads Google Fonts and Next.js inline bootstrap code. A staged policy must first be added as `Content-Security-Policy-Report-Only` on a deployed staging origin with a reporting endpoint; collect violations while testing every customer, staff, admin, order, and QR flow; then introduce nonces or hashes and an explicit source allowlist for scripts/styles and self-hosted or explicitly allowed image/font/connect sources. Enforce the policy on staging, monitor violations, then roll out to production with rollback. Enable HSTS only at the verified HTTPS deployment edge after certificate, redirect, and host configuration checks; leave it off on local HTTP and any unverified domain. Do not add `includeSubDomains` or preload until every subdomain is verified HTTPS-only. |
| Medium | Authenticated/customer-specific APIs relied on handler-level behavior for cache policy. | Next.js now sends `Cache-Control: private, no-store, max-age=0` on API paths. Integration checks verify protected customer and management responses are not cacheable. | Check any future CDN/reverse proxy configuration preserves the no-store directive. |
| Medium | Staff login parsed form bodies before applying input limits; a missing or false `Content-Length` could leave a streamed body unbounded. | The handler now accepts URL-encoded login forms only, caps declared and streamed bodies at 8 KiB, rejects duplicate/malformed fields, and limits email/password input. Integration tests cover both declared oversize and chunked oversize bodies; both return 400 before database lookup. | The login page currently uses standard URL-encoded form submission, matching the accepted media type. |
| Medium | Reservation availability queried table occupancy sequentially for each of six candidate slots. | Availability now performs one bounded occupancy query for the span of valid candidate windows and calculates each slot from that result. Pure unit coverage checks overlap and touching interval boundaries; Phase 10.1 concurrency integration remains green. | The endpoint is advisory; transactional booking allocation and the database exclusion constraint remain authoritative. |
| Low | Customer order, QR, kitchen, and floor changes were not consistently announced to assistive technology; focus indication and some mobile controls needed clearer targets. | Added generic polite announcements for order/kitchen/floor updates, QR cart-count announcements, forest/gold focus-visible outlines, and 44 px minimum controls for small buttons, floor actions, and QR quantity controls. New live announcements contain only generic status text or item counts, not guest names, contact details, or order contents. Unit tests assert the announcement markup, focus rules, and touch-target sizes. | The existing selected floor-table detail panel remains visible to already-authorized staff and includes guest/table details; it is not part of the new generic live announcement. No browser, screen-reader, or keyboard-only acceptance session was available. Manual review remains required; WCAG 2.2 AA is not claimed. |
| Low | Availability accepted syntactically shaped but impossible dates until deeper business logic. | Strict calendar-date and party-size validation now runs before database work; a development and production HTTP integration check verifies `2026-02-30` returns 400. | None identified in this path. |

Existing same-origin mutation validation was retained and live-tested: missing and foreign `Origin` values return 403. Server-side role and restaurant authorization code was not changed by this hardening diff. Session tests continue to cover hashed tokens, expiry, revocation, active-account checks, and HttpOnly/SameSite/Secure cookies.

## Local response-time observations

Seven sequential local production-mode samples were taken on the same machine. Before integration suites changed the fixture population, medians/p95 were `/` 35.6/40.8 ms, `/menu` 46.3/60.8 ms, and availability 19.1/24.9 ms. After running the suites and warming the server, medians/p95 were approximately `/` 185.9/249.3 ms, `/menu` 161.4/179.6 ms, and availability 36.2/110.2 ms. These are local smoke measurements, not a production load test; the database now contains additional test-created fixtures and the runs are not directly comparable. No latency SLO or throughput claim is made.

## Database baseline drift

The read-only schema diff showed extensive pre-existing differences in defaults, timestamp types, foreign keys, and index names/presence, including occupancy and waitlist index differences. Migration status remained current. This work added no migration and made no database changes beyond the established integration fixtures/cleanup performed by their own suites. No broad cleanup, reset, or schema reconciliation was run.

## Manual follow-up

Before release, test keyboard-only operation, visible focus on all interactive controls, live-region announcements with the supported screen readers, mobile tap targets, and CSP behavior in the deployment environment. Confirm the trusted client-IP header is stripped from inbound requests and overwritten by the ingress, and verify the origin cannot be reached around that ingress. Verify TLS certificates, redirects, and host routing on the public HTTPS origin before enabling HSTS at the deployment edge. The CSP report-only, violation review, staging enforcement, and production rollout described above are release work; WCAG 2.2 AA requires a separate suitable audit and is not verified here.
